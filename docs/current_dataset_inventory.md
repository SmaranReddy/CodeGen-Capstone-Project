## 0. Headline findings

1. **There is no NL→SQL training set, and no NL→SQL experiment has ever been run.**
   - Every experiment so far (`outputs/evaluation_*`, `outputs/rag_week3*`) generated **MQL**. The `mql` field is in every executions file.
   - Gold SQL was used only as the *reference executor* for scoring MQL.
2. **The only clean, schema-grounded native NL→SQL training pool on disk is Spider 1.0 train.**
   - It is `train_spider.json` (7,000) plus `train_others.json` (1,659), which gives **8,659 records** on **146 databases**.
   - All 146 SQLite files are present and readable.
   - It has **zero** database overlap with Spider dev (20 DBs) and Spider test (40 DBs).
   - **1,759 of these records sit on DBs whose tables are all empty**: all 1,659 `train_others` records, plus 100 records on `music_2`. Execution-based label checks cannot validate them on the shipped DBs. The test-suite zip has populated variants for 5 of these DBs: one variant per DB was checked and holds rows. See §2.A.
   - None of the 8,659 has been used for SQL training. None has been re-validated for the SQL task.
3. **The 455-example "expanded benchmark" is drawn entirely from Spider *dev*.**
   - Its 318/72/65 split is a re-partition of 20 Spider-dev databases.
   - If the primary NL→SQL benchmark is Spider dev, **none of the 455 can be used for SQL training**, including the 318 "train" partition. Using them would contaminate the standard Spider-dev evaluation.
   - The same applies to the 280 Spider rows in `data/finetune/ft_v1/train.jsonl` and to the 280 RAG examples. All of them are Spider-dev items.
4. **The 280 Spider "examples" in ft-v1 and the RAG corpus hold model-predicted MQL, not gold.**
   - 265 come from gpt-oss-120b and 15 from Qwen2.5-Coder-7B. Each was kept because it execution-matched the gold-SQL result.
   - Only the original v1 set (`spider1_nl_mql.jsonl`, 279) carries authored `gold_mql`.
5. **BIRD has not been collected.**
   - No BIRD file, archive or cache exists in the repo or in `~/.cache/huggingface`.
   - BIRD appears only in the research docs (`docs/dataset_research_report.md`, `docs/native_nl2mql_dataset_research.md`).
6. **The Kaggle NL2SQL set is not validated for the SQL task.**
   - It has 14,815 raw rows and 4,337 unique pairs after repair.
   - It has no schema and no database. It has placeholders, row-shifted labels and SQL-level date-equality errors.
   - Its licence is **CC BY-NC-SA 4.0** (non-commercial). The "fixture-equivalence verified" status means only that the converter's MQL matched the SQL on synthetic fixtures. It does *not* show that the SQL answers the question.
7. **Native NL→MQL data collected: 0.** TEND, AptMQL, SM3, DocSpider and the others were researched only.
8. **No fine-tuning run exists.**
   - `models/` holds only two quantised GGUF base models.
   - There are no adapters, checkpoints or `.safetensors` files in the repo.
   - `scripts/finetune_v1/train_qlora.py` exists but has not been run.

### E. SQL→MQL conversion dataset (ft-v1, derived from Kaggle)

**Code.** `scripts/finetune_v1/`, run as extract → verify → build_ft. The main modules are `sql2mql.py`, `sqlsem.py`, `fixtures.py` and `verify.py`. Code hashes are pinned in `build_manifest.json`.

**Verification method.**
- The reference SQL runs on SQLite with MySQL-semantics UDFs.
- The converter's MQL runs on MongoDB 8.0 `$documents`.
- Both run over mutant-adequate synthetic fixtures.
- Status label: **`fixture_equivalence_verified`**. It is never source-DB execution.

**Funnel.** All figures Verified from `status_manifest.jsonl` (4,337 rows) and the output files.

| Stage | Count |
|---|---:|
| Unique Kaggle pairs | 4,337 |
| Stage-1 eligible (sent to the converter and verifier) | 2,621 |
| Not eligible | 689 ambiguous, 484 rejected, 543 unsupported (543 + 28 = 571 in `candidates_unverified.jsonl`) |
| Verifier result on eligible | 2,561 fixture-equivalence verified, 32 failed execution, 28 unverified (Manifest) |
| Verified, then removed as duplicate after conversion | 13, leaving 2,548 verified unique (Verified) |
| Near-duplicate cap (3 per cluster) | **1,584 kept**, 964 capped out (`verified_capped_near_dups.jsonl`, 964 Verified) |
| Kept split | 1,504 → `train.jsonl`; 80 → `dev_internal.jsonl` (Verified) |
| `rejected.jsonl` | 1,218: 689 ambiguous + 484 rejected + 32 failed + 13 duplicates (Verified) |

- `verify/progress.jsonl` has 10,878 lines over 7 code versions. Its latest status covers 2,622 pairs.
- One of those pairs was verified there but later reclassified as `rejected` in the final manifest. That accounts for both off-by-one differences: 2,622 vs 2,621 eligible, and 2,562 vs 2,561 verified. The difference is benign but undocumented.

**The 1,584 are not all correct (independent audit, `outputs/audit_sql2mql_v1/summary.json`, Verified).**
- **88 of 1,584 (5.6%, Wilson 95% interval 4.5–6.8%) are wrong** under explicit-NULL semantics. Both bugs:
  - B1: an ungrouped aggregate over zero rows returns no document (84 labels);
  - B2: SUM over all-NULL input returns 0 instead of NULL (20 labels);
  - 16 labels have both.
  - 6 of the 88 fail even on non-degenerate random data.
- 62 labels fail if NULL is stored as a missing field.
- 51 labels carry SQL-level `datetime = date` errors.
- **Verifier blind spots:**
  - it accepted 10 of 20 wrong adversarial translations;
  - in the mutant study, 21 of 200 labels (10.5%, interval 7.0–15.5%) have a non-equivalent MQL mutant that the verifier accepts.
- The 1,584 are therefore **"converter output that passed a verifier with known weaknesses"**. They are not verified-correct labels. The 1,496 not flagged by the audit are still unproven: only the census checks were run on them.

## 4. Answers

**1. What is our exact current primary NL→SQL inventory?**
- Spider 1.0 in full:
  - train: 8,659 records, 146 DBs;
  - dev: 1,034 records, 20 DBs;
  - test: 2,147 records, 40 DBs;
  - schemas and SQLite DBs for all 206 DBs;
  - test-suite DBs: 3,194 variants for 28 DBs, of which 57 are extracted.
- Kaggle NL2SQL: 4,337 unique pairs, with no schema or DB.
- 24 Spider2-Lite local gold pairs.
- The 455 and 279 benchmarks are filtered Spider-dev subsets. They are not additional data.

**2. How much is suitable for SFT today?**
- **None is validated yet.**
- The practical candidate is Spider train:
  - 8,659 records, or 6,900 if limited to the DBs that are not empty;
  - official gold labels and real DBs;
  - CC BY-SA licence;
  - it still needs execution re-validation and deduplication before it becomes an SFT set (§5).
- Kaggle should not be merged in its current state.
- No Spider-dev-derived record (the 455, the 318, ft-v1's 280, the RAG examples) may be used if Spider dev is the evaluation set.

**3. Have we collected BIRD?** **No.** It has only been discussed. No file, archive or cache exists.

**4. What additional records or assets are needed?**
- To make Spider train usable:
  - execution re-validation on the shipped DBs;
  - populated DBs for the 1,759 empty-DB records. The test-suite zip may cover 5 of the 6 `train_others` DBs, and `music_2` is not covered;
  - deduplication;
  - a dev-overlap screen.
- For BIRD:
  - train JSON (9,428), or the filtered train (6,601);
  - its SQLite DBs (about 33 GB for the full set);
  - dev (1,534) as a second benchmark.
- An internal validation split drawn **from Spider train DBs**, so that Spider dev stays a clean benchmark.

**5. Which sources next, and why?**
1. **Spider train, already on disk.** It has the highest quality, the same distribution as the benchmark, and DBs present. It needs no download.
2. **BIRD train (or bird23-train-filtered) plus dev.** It is the second named benchmark, it is larger and harder, and it carries `evidence` hints. Cost: a large download, and its licence must be confirmed at source.
3. **SParC/CoSQL self-contained turns** (Spider-train DBs only). These are optional extra paraphrases with low marginal value. Their dev sets must be excluded.

The following stay rejected for the SQL track:
- Kaggle (NC licence, no schema);
- WikiSQL (single-table);
- `sql-create-context` (it contains Spider dev).

**6. Issues to resolve before combining.**
- **Split hygiene.**
  - Decide the official evaluation set: Spider dev, Spider test, or BIRD dev.
  - Then exclude every derivative of it, including the 455/318/280 artifacts if it is Spider dev.
  - Screen the 7 dev/train and 25 test/train shared questions.
- **Empty DBs.** 1,759 train records cannot be execution-checked on the shipped DBs.
- **Dialects.** Spider uses SQLite. Kaggle uses MySQL. BIRD uses SQLite. Spider2 non-local data uses BigQuery or Snowflake.
- **Schema format.** Spider uses `tables.json`. BIRD has its own schema format and description CSVs. Kaggle has none.
- **Licences.**
  - Spider and BIRD are CC BY-SA 4.0 (ShareAlike).
  - Kaggle is CC BY-NC-SA 4.0 (non-commercial).
  - BY-SA 4.0 lists only BY-SA-compatible licences, and BY-NC-SA is not one of them (per CC's published compatibility list; not re-fetched in this audit). A merged corpus therefore cannot carry one clean licence. Keep the sources in separate files.
  - Spider's licence is not in the local files. Record it, with its source, in a manifest.
- **Duplicates.**
  - 8 exact duplicate records in `train_spider`.
  - Many questions per SQL: 8,659 records but only 4,727 distinct (db, SQL) pairs.
  - Decide whether paraphrase multiplicity is wanted.
- **Kaggle label noise** (if it is ever used): placeholders, row-shifts, date-equality errors, conflicting SQL on 103 questions.

**7. Best next step before any fine-tuning experiment.**
- Build a **Spider-train NL→SQL SFT candidate set** as a new versioned artifact, for example under `data/finetune/sql_v1/`. Leave existing data untouched.
- Steps:
  1. Execute every gold SQL read-only on its shipped DB. Record row counts, errors and empty results.
  2. Assess whether the test-suite zip's populated `academic`/`imdb`/`restaurants`/`scholar`/`yelp` variants can validate `train_others` labels. They are confirmed to hold rows; whether they suit this purpose is not yet established.
  3. Deduplicate.
  4. Screen for question overlap against dev and test.
  5. Carve a DB-disjoint internal validation split from the train DBs.
  6. Write a manifest with source hashes and the licence.
- Separately, decide and record whether the benchmark is Spider dev, BIRD dev or both. This decision fixes which existing artifacts become evaluation-only.
- Only after that, run a zero-shot **SQL** baseline on dev with the existing Qwen models, so that any later fine-tune has a reference point.
- BIRD collection should follow as a separate, explicitly approved download.

## 5. Unresolved questions and limitations of this audit

- **Not executed.** Spider train gold SQL has not been run on its DBs in this audit (it was run in the MQL census only, as 4,731 unique rows), so the execution-validity rate of the 8,659 for SQL SFT is unknown.
- **Not checked.** It is unknown whether the test-suite variants for the `train_others` DBs are suitable as validation backends. One variant per DB was confirmed to hold rows; the other variants were not opened. They were built as evaluation suites (Zhong et al.), and their use for training labels has not been assessed.
- **Kaggle row-shift prevalence** has never been measured directly for SQL correctness. The 60-record manual review judged MQL labels.
- **Licences.** Spider (CC BY-SA 4.0) and BIRD (CC BY-SA 4.0) come from earlier research docs and were not re-fetched. Kaggle's licence comes from API metadata, not a file. Spider 2.0's *data* licence is unverified.
- **Off-by-one in verify progress** (§2.E). The difference is benign but is not recorded in any manifest.
- **Normalisation scope.** The duplicate counts use light normalisation (case, whitespace, trailing punctuation). Semantic or near-duplicate SQL equivalence across sources was not computed. The only cross-source check was exact normalised matching: Kaggle↔Spider shared 0 questions and 1 SQL string, and Spider2↔Spider1 shared 0 questions.
- The inventory script is not committed to the repo. It was run from a scratch directory, so the counts here can be reproduced only by re-running equivalent read-only code.
